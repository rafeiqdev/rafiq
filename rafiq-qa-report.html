أي شخص يستطيع تفعيل اشتراك «إيليت» لأي مستخدم — بدون تسجيل دخول أصلًا

قاعدة البيانات · الدالة _activate_sub · تجاوز كامل للصلاحيات

الوصف

الدالة public._activate_sub(p_uid, p_tier, p_billing, p_days) معرّفة بـ SECURITY DEFINER ولا تحتوي على أي تحقق من الهوية أو الصلاحية — لا is_admin() ولا auth.uid(). ومع ذلك صلاحية التنفيذ عليها ممنوحة للدورين anon وauthenticated، أي أنها مكشوفة عبر POST /rest/v1/rpc/_activate_sub باستخدام المفتاح العام الموجود في كود الواجهة.

النتيجة: زائر مجهول تمامًا يستطيع منح نفسه — أو أي حساب — أي باقة لأي مدة، وإلغاء أي اشتراك، دون أن يمرّ بأي عملية دفع.

الدليل

-- تعريف الدالة كما هي على الإنتاج الآن
CREATE FUNCTION public._activate_sub(p_uid uuid, p_tier text, p_billing text, p_days integer)
  RETURNS void LANGUAGE plpgsql SECURITY DEFINER
AS $$ begin
  insert into public.subscriptions (...) values (p_uid, p_tier, p_billing, 'active', ...)
  on conflict (user_id) do update set tier = excluded.tier, status = 'active', ...;
end $$;
-- لا يوجد أي سطر تحقق صلاحية

has_function_privilege('anon',          '_activate_sub', 'EXECUTE') -> true
has_function_privilege('authenticated', '_activate_sub', 'EXECUTE') -> true

ملاحظة: لم أنفّذ الاستغلال على قاعدة البيانات الحيّة — الإثبات مبني على قراءة تعريف الدالة وصلاحياتها فقط.

الإصلاح

REVOKE EXECUTE ON FUNCTION public._activate_sub(uuid,text,text,integer) FROM anon, authenticated;
REVOKE EXECUTE ON FUNCTION public._credit_referrer(uuid,text,integer)   FROM anon, authenticated;
-- الدوال الداخلية (المسبوقة بـ _) يجب ألا تكون في الـ API العام إطلاقًا

أي شخص يستطيع صرف عمولات إحالة وهمية (٣٠٪ نقدية) لأي حساب

قاعدة البيانات · الدالة _credit_referrer

_credit_referrer(p_uid, p_payment_id, p_amount) — نفس المشكلة: SECURITY DEFINER، بلا تحقق صلاحية، ومكشوفة لـanon. وبما أن برنامج الإحالة يدفع نقدًا (٣٠٪)، فهذه ثغرة مالية مباشرة وليست تجميلية.

المعمارية الموثّقة ليست هي المنشورة — كل حماية الخادم غير مفعّلة على الإنتاج

معمارية · README مقابل الواقع

ملف README يصف خادم Express يتخذ «كل قرارات الثقة»: bcrypt، جلسات مخزّنة، Webhook موقّع بـHMAC، و402 على الميزات المدفوعة. اختبرتُ هذا الخادم محليًا وهو ممتاز فعلًا:

الاختبارالنتيجة محليًا
تزوير Webhook بلا توقيع401 bad_signature ✓
مستخدم عادي يطلب /api/admin/*403 forbidden ✓
مستخدم مجاني يطلب /api/places402 upgrade_required ✓
حد رسائل الذكاء الاصطناعي المجانية3 رسائل ثم 402 ✓
رفع ملف .exe400 bad_file_type ✓
حجز موعد في الماضي400 past_datetime ✓
إعادة تنفيذ نفس الدفعةلا يتكرر التفعيل ✓

لكن هذا الخادم غير منشور. مجلد api/ على Vercel يحتوي فقط على ai-chat وplaces-search وplace-photo وcron. الموقع الحيّ يحمّل supabase-js (212 كيلوبايت) ويتحدث مع القاعدة مباشرة. أي أن كل الحماية أعلاه لا تحمي المستخدم الحقيقي — وهذا هو السبب الجذري للثغرات الثلاث في القسم الأول.

التوصية

اتخذ قرارًا واضحًا: إما نشر خادم Express وجعل الواجهة تتحدث معه فقط، أو الالتزام بـSupabase ونقل كل منطق الدفع/التفعيل إلى Edge Function بمفتاح service role. الوضع الحالي (الاثنان معًا) هو الأسوأ لأنه يوحي بأمان غير موجود.

الصور تختفي في أغلب الزيارات — صورة الغلاف تظهر مستطيلًا أزرق فارغًا

واجهة · src/components/SiteImage.tsx

الوصف

هذا أوضح خلل بصري في الموقع. عند فحص الصفحة الرئيسية وجدتُ الصور الأربع في carousel الغلاف كلها بـopacity: 0 رغم أن complete = true — أي أنها حُمِّلت بالكامل لكنها غير مرئية. ونفس الشيء لصورة قسم «من نحن» التي تظهر مربعًا رماديًا فارغًا.

// النتيجة الفعلية من المتصفح على rafiq.ist
{ src: "1524231757912-….webp", opacity: "0", complete: true }
{ src: "1527838832700-….webp", opacity: "0", complete: true }
{ src: "1541432901042-….webp", opacity: "0", complete: true }
{ src: "1518105779142-….webp", opacity: "0", complete: true }

السبب الجذري

المكوّن يبدأ بـopacity-0 ولا ينتقل إلى opacity-100 إلا داخل onLoad. وعندما تأتي الصورة من الـcache (أي في كل زيارة متكررة) يقع حدث load قبل أن يربط React المستمع، فلا يُستدعى onLoad أبدًا وتبقى الصورة شفافة إلى الأبد — مع بقاء هيكل التحميل النابض فوقها.

الإصلاح

const ref = useRef<HTMLImageElement>(null);
const [loaded, setLoaded] = useState(false);

useEffect(() => {
  if (ref.current?.complete && ref.current.naturalWidth > 0) setLoaded(true);
}, []);

<img ref={ref} onLoad={() => setLoaded(true)} … />

وأيضًا: صورة الغلاف تستخدم loading="lazy" — وهي عنصر LCP. يجب أن تكون loading="eager" مع fetchpriority="high".

لا توجد ميزة «نسيت كلمة المرور» في المنتج كله

المصادقة · /auth

صفحة تسجيل الدخول تعرض: Google، بريد، كلمة مرور، زر دخول، ورابط إنشاء حساب. لا يوجد رابط استعادة كلمة مرور، ولا مسار reset في الخادم، ولا مفتاح ترجمة يقابله في أي من ملفات اللغات الأربعة.

لمنتج باشتراك شهري مدفوع، هذا يعني أن كل مستخدم ينسى كلمته يصبح تذكرة دعم يدوية — أو عميلًا مفقودًا. مع Supabase Auth الحل جاهز: resetPasswordForEmail().

ملاحظة مرتبطة: Supabase يبلّغ أن Leaked Password Protection معطّلة — يُنصح بتفعيلها.

وسوم hreflang معطّلة — اللغات الأربع تشير كلها لنفس الرابط

تحسين محركات البحث · sitemap.xml

هذه أكبر مشكلة تسويقية في المشروع. اللغة محفوظة في localStorage فقط، ولا يوجد مقطع لغة في الرابط. لذلك كل مدخلة في sitemap تبدو هكذا:

<loc>https://rafiq.ist/services</loc>
<xhtml:link rel="alternate" hreflang="ar" href="https://rafiq.ist/services" />
<xhtml:link rel="alternate" hreflang="en" href="https://rafiq.ist/services" />
<xhtml:link rel="alternate" hreflang="ru" href="https://rafiq.ist/services" />
<xhtml:link rel="alternate" hreflang="fa" href="https://rafiq.ist/services" />

محرك البحث يرى أربع لغات على رابط واحد، فيفهرس نسخة واحدة فقط ويتجاهل الباقي. أنتم تدفعون تكلفة ترجمة ١٢٤٠ مفتاحًا × ٤ لغات ولا تحصدون منها أي زيارات عضوية بالروسية أو الفارسية أو الإنجليزية.

الإصلاح

اعتماد مسار لغة: /ar/services، /en/services … مع إعادة توجيه من الجذر حسب Accept-Language، وتحديث مولّد sitemap ليولّد رابطًا لكل لغة. هذا يفتح ٤ أضعاف السطح للفهرسة.

مرتبط: og:locale مضبوط على ar_AR وهي قيمة غير صالحة (الصحيح ar_SA أو ar_AE).

الأدمن لا يرى أي سجل للدفعات — فقط المعلّقة

لوحة التحكم · /api/admin/payments
 
SELECT * FROM payments WHERE status = 'pending' ORDER BY created_at DESC

لا توجد أي شاشة لعرض الدفعات المؤكدة أو المرفوضة أو الإيرادات. عمليًا: لا يمكن معرفة كم دخل هذا الشهر، ولا مراجعة نزاع، ولا تتبّع عمولة إحالة. أنصح بإضافة تبويب «كل الدفعات» مع فلتر حالة وتاريخ ومجموع.

متوسط

رفض دفعة حقيقية بصمت مع إرجاع 200 OK

لوحة التحكم · /api/admin/payments/:id/resolve

اكتشفتُ هذا بالخطأ أثناء الاختبار: أرسلتُ {"action":"approve"} بدل {"status":"verified"}، فردّ الخادم {"ok":true} بينما كان قد رفض الدفعة فعليًا.

if (req.body?.status === 'verified') settleVerifiedPayment(p);
else db.prepare("UPDATE payments SET status = 'rejected' …").run(p.id);  // ← الافتراضي: رفض
res.json({ ok: true });

أي خطأ مطبعي أو تغيير في الواجهة سيرفض دفعات حقيقية دون أن يلاحظ أحد. يجب التحقق الصريح: if (!['verified','rejected'].includes(status)) return 400، وإرجاع الحالة الجديدة في الرد.

مشكلة مشابهة: POST /api/admin/users/:id/tier يُرجع ok:true حتى لمعرّف مستخدم غير موجود، وينشئ صفّ اشتراك يتيم.

الصفحات المقفلة تعرض بطاقة عامة بلا أي معاينة أو سياق

تحويل · /map، /journey وغيرها

عند فتح الخريطة أو الرحلة يظهر مربع أبيض صغير: قفل + «تسجيل الدخول مطلوب» + زر. نفس البطاقة حرفيًا في كل الصفحات المقفلة — لا صورة، ولا عيّنة، ولا ذكر لما وراء الجدار.

الزائر لا يعرف أن الخريطة تحتوي مطاعم ومستشفيات وبنوكًا موصى بها، فلا يجد سببًا للتسجيل. البديل المعتاد: خريطة ضبابية مع ٣ دبابيس مرئية + «افتح ٥٠+ موقعًا موثوقًا». التعليق في الكود يذكر أن نسخة سابقة كانت تفعل ذلك بالضبط — أرى أن إزالتها كانت خسارة تحويل.

محتوى مقصوص وحشوة مكرّرة على الموبايل

موبايل · عرض 390 بكسل
  • صف الشارات تحت العنوان («٤ لغات / دعم خبراء / مكالمة مجانية…») مقصوص عند حافة الشاشة بلا مؤشر تمرير أفقي.
  • زر البحث (مربع داكن) يلتصق بحافة حقل البحث بنصف قطر مختلف — يبدو غير محاذٍ.
  • صفحة الخدمات تعرض شريحتَي «الكل» متطابقتين شكلًا في صفّين مختلفين (فلتر المزوّد وفلتر التصنيف) — على سطح المكتب أيضًا. تحتاج عناوين للصفّين.

إيجابي: شريط التبويب السفلي بخمسة عناصر تجربة أصيلة وجيدة، والشاشات المخصّصة للموبايل (وليس مجرد responsive) قرار قوي.

تحسين

بوابة اللغة تحجب كل المحتوى عند أول زيارة

تجربة · الصفحة الأولى

أول ما يراه الزائر شاشة زرقاء فارغة عليها أربعة أزرار في منتصف صفحة شبه خالية. لا شعار قيمة، ولا صورة، ولا أي فكرة عن ماهية الموقع. الفراغ العمودي كبير جدًا والبطاقة غير متوازنة بصريًا.

البديل الأفضل: اكتشاف اللغة من Accept-Language تلقائيًا، عرض الموقع مباشرة، ووضع مبدّل اللغة بارزًا في الترويسة (وهو موجود أصلًا). هذا يزيل خطوة كاملة من قمع التحويل ويحسّن الانطباع الأول.

صفحة الباقات: لا باقة مجانية، ولا جدول مقارنة، ولا سعر بالدولار

تسعير · /pricing

التصميم نفسه جيد: ثلاث بطاقات، شارة «موصى به» على «برو»، ومبدّل شهري/سنوي يعمل بشكل صحيح ويُظهر «شهران مجانًا». تحققتُ من الحساب: 1,599 × 10 = 15,990 ÷ 12 = 1,333 ✓ — الرياضيات سليمة.

لكن:

  • الباقة المجانية غير معروضة مطلقًا، فلا يعرف الزائر ماذا يحصل بلا دفع.
  • كل باقة ٤–٥ نقاط فقط، و«إيليت» تقول «كل ما في برو» — لا يوجد جدول مقارنة يوضح الفرق.
  • الأسعار بالليرة فقط، رغم أن الموقع يعرض شريط صرف حيّ في الأعلى والجمهور أجنبي. عرض «≈ 34 دولارًا» بجانب السعر قرار تحويل سهل ومباشر.
  • صياغات مثل «استشارات ذكاء اصطناعي بلا حدود» تحتاج تحديدًا (ما الحدّ العادل؟).

آراء العملاء حقيقية لكن عرضها لا يُقنع الزائر بذلك

ثقة · الصفحة الرئيسية

تصحيح من صاحب المشروع: هذه شهادات عملاء حقيقيين خدمهم بنفسه قبل إطلاق الموقع. الملاحظة أدناه عن طريقة العرض فقط، لا عن صحّة المحتوى.

المشكلة أن العرض الحالي يحمل كل علامات الشهادات المُصطنعة: شهادة واحدة بالضبط لكل لغة مستهدفة (سوريا / روسيا / إيران)، خمس نجوم في الثلاث، أحرف أولى فقط، بلا صور ولا تواريخ ولا أي رابط. الزائر الذي لا يعرفك سيقرأها كنص تسويقي مكتوب، فتضيع قيمتها الحقيقية.

كيف تُظهر أنها حقيقية

  • الاسم الأول كاملًا + الحرف الأول من العائلة، مع صورة حقيقية أو الأحرف الأولى بخط اليد.
  • تاريخ الخدمة ونوعها تحديدًا: «إقامة سياحية — مارس ٢٠٢٦» بدل «طالب من سوريا».
  • تفصيلة ملموسة داخل النص (اسم الحي، عدد الأيام، عقبة حُلّت) — التفاصيل هي ما يميّز الشهادة الحقيقية عن المكتوبة.
  • عدد فردي وغير متساوٍ من الشهادات (٥ أو ٧)، وليس ٤ تقابل ٤ لغات.
  • الأقوى: رابط تقييم Google Business أو لقطة محادثة WhatsApp بموافقة العميل — دليل خارجي لا يمكن تأليفه.

أما الأرقام «+١٠٠٠ مستخدم» و«+٢٠ معاملة» فتحتاج أن تكون قابلة للدفاع عنها إن سُئلت، ويفضَّل ربطها بفترة زمنية: «أكثر من ١٠٠٠ حالة منذ ٢٠٢٣».

تفاصيل تصميم متفرّقة

هوية بصرية وتلميع
  • theme-color في index.html هو #1d5f9e بينما لون الهوية الأساسي #1a3a6b — شريط المتصفح على الهاتف يظهر بلون مختلف عن الموقع.
  • شعار الترويسة رابط بلا نص بديل مفيد (alt فارغ عمليًا للقارئ الآلي).
  • جرس الإشعارات يظهر للزائر غير المسجّل ولا يفعل شيئًا مفيدًا.
  • لافتة الكوكيز تحتل شريطًا كبيرًا أسفل الشاشة وتغطي المحتوى على كل صفحة حتى الرد عليها، وليس فيها زر إغلاق (×) — فقط «موافق» أو «لا شكرًا».
  • setInterval كل ثانية في Premium و MobilePremium يسبب إعادة رسم مستمرة — يُفضّل تحديث كل دقيقة أو استخدام CSS.
  • سهم زر «العودة إلى الرئيسية» في صفحة 404 يشير يسارًا داخل تخطيط عربي — يُفضّل عكسه في RTL.

٥ · ما يعمل جيدًا فعلًا

جيد

نقاط قوة حقيقية يجب الحفاظ عليها

ملخّص إيجابي
  • جودة الكود والاختبارات: ٤٧٩ اختبار وحدة + ١١ اختبار خادم كلها ناجحة، tsc نظيف بلا أخطاء، وتطابق مفاتيح الترجمة ١٢٤٠ مفتاحًا × ٤ لغات مفروض آليًا في CI. هذا انضباط أعلى من أغلب المشاريع المشابهة.
  • خادم Express المحلي: نموذج أمني ممتاز — تحقق توقيع HMAC، تفعيل عبر Webhook فقط، حصر الوصول للمالك، تحقق نوع الملف، رفض التواريخ الماضية، ومنع التكرار. يستحق أن يُنشر.
  • الترجمة والتخطيط: النسخ الروسية والإنجليزية نظيفة ومنعكسة بشكل صحيح، والعربية RTL سليمة في معظم الشاشات. مستوى الترجمة نفسه (ليست حرفية) جيد جدًا.
  • المحتوى: الأدلة (الإقامة، الرقم الضريبي، البنك، الأحياء) مكتوبة بمعرفة حقيقية بالسوق التركي — تحذير «تحقق أن حيّك مفتوح قبل توقيع عقد الإيجار» هو بالضبط النصيحة التي تصنع الفرق. هذا أقوى أصل في المشروع.
  • الموبايل: شاشات مخصّصة كاملة وليست مجرد تجاوب، مع شريط تبويب سفلي.
  • إمكانية الوصول: إبقاء تكبير الشاشة بالإصبعين عمدًا مع توثيق السبب واختبار يحرسه.
  • البنية التقنية: TTFB 130 مللي ثانية، تقسيم حزم منطقي حسب الصفحة، sitemap بـ٩٦ رابطًا، robots.txt مولّد آليًا من متغير البيئة (حل ذكي لمشكلة عدم تطابق النطاق).
